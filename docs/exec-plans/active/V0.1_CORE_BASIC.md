## 1. Purpose and user-visible outcome

Deliver a portable native-style desktop application that lets a user safely prepare and perform basic management of a fresh Ubuntu VPS without memorizing Linux commands.

At the v0.1 Owner-test boundary, a user can:

1. launch a self-contained VPSReady desktop artifact on a supported local platform;
2. enter host/IP, SSH port, username, and password;
3. explicitly establish SSH host trust and test a real connection;
4. inspect useful Ubuntu server facts and privilege/firewall state;
5. view, add, remove, enable, and disable basic UFW rules without cutting off the active SSH connection;
6. create a local ED25519 key pair safely;
7. deploy the public key without damaging existing access and verify a separate key-authenticated connection;
8. create/update a local OpenSSH alias while preserving unrelated configuration;
9. perform approved basic Ubuntu system actions with confirmation, progress, verification, cancellation, and sanitized diagnostics;
10. distinguish success, failure, cancellation, and recovery-required outcomes.

A release candidate is not ready merely because it builds. Required automated, disposable-Ubuntu, Manual QA, packaging, security, and Principal evidence must exist.

## 4. Scope

### Included

- C#/.NET 10 LTS solution.
- Avalonia desktop UI.
- Windows, macOS, and Linux self-contained deliverables.
- Ubuntu remote targets only.
- Password-based initial SSH connection.
- Explicit SSH host-key trust/change handling.
- Server overview.
- Basic UFW firewall management.
- ED25519 local key generation.
- Public-key deployment and separate key-login verification.
- Local OpenSSH config alias management.
- Basic package/system actions approved by the product spec.
- Activity/progress/diagnostic logging with secret redaction.
- Safety, cancellation, timeout, idempotency, verification, and recovery behavior.
- CI, automated tests, disposable Ubuntu E2E, packaging, and user documentation.

### Explicitly excluded

- Docker/Compose, Coolify, Fail2ban.
- Nginx/Apache/Caddy or databases.
- Kubernetes.
- Cloud-provider provisioning/snapshots.
- DNS/TLS/domain automation.
- Monitoring, telemetry, analytics, accounts, advertising.
- Hosted frontend/backend or persistent remote VPSReady agent.
- Multi-distribution support.
- Stable production signing/notarization without Owner credentials/approval.
- Shipping CLI in v0.1.
- Arbitrary shell/terminal feature.
- Disabling password/root SSH access unless separately added to approved scope.

Out-of-scope discoveries become backlog issues.

## 5. Release-blocking safety constraints

- No silent SSH host-key acceptance.
- Changed known fingerprint fails closed until explicit review.
- No password/private-key leakage to logs, persistence, issues, tests, screenshots, or artifacts.
- No firewall enable before active SSH allow-rule verification.
- No ordinary removal/blocking of active SSH port.
- No success before practical state verification.
- No destructive overwrite of existing SSH config or `authorized_keys`.
- No mock-only proof for lockout-sensitive release behavior.
- No destructive operation without explicit user action.
- No lockout E2E on personal/production infrastructure without Owner authorization.

## 6. Major-gate policy

There are only three outer gates.

### Gate A — first complete connection workflow (#9)

After M2: Automation regression → Manual QA → Principal. Proves launch, host trust, real password connection, understandable failures, and server overview.

### Gate B — access-safety workflow (#10)

After M3+M4: Automation regression → Manual QA → Principal. Proves firewall and SSH-key/config operations preserve access and are interoperable/idempotent.

### Gate C — final release readiness (#11)

After M5+M6: full Automation regression → final Manual QA → Principal. Principal creates `release/0.1.0` from exact approved `development` SHA.

M0, M1, and routine cards do not receive Manual/Principal gates unless a genuine escalation meets `docs/agents/WORKFLOW.md`.

Expected minimal shape:

```text
src/
  VpsReady.Desktop/

  VpsReady.Core/
  VpsReady.Infrastructure/

tests/
  VpsReady.UnitTests/
  VpsReady.IntegrationTests/
```

The implementation may simplify names/projects while preserving UI/infrastructure separation, independent application testing, isolated Ubuntu/UFW/SSH adapters, centralized quoting/redaction/results, and no raw remote commands in views. Pin dependencies centrally and document licenses/maintenance.
