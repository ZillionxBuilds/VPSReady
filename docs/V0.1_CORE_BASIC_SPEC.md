# VPSReady v0.1 Core Basic Specification

Status: **Approved development scope for `development` — Blind Development Edition**

This document is the implementation contract for VPSReady Core Basic v0.1. Autonomous development must remain inside this scope unless the Owner explicitly changes it.

## 1. Product goal

VPSReady v0.1 is a portable cross-platform desktop application that helps a user connect to a fresh Ubuntu VPS, inspect it, establish safe SSH access, manage basic firewall rules, perform basic system actions, and leave the VPS in a usable and safer state without requiring the user to memorize Linux commands.

The application runs locally on Windows, macOS and Linux and manages the VPS over SSH. No permanent VPSReady process is installed on the remote server.

## 2. Binding blind-development constraint

The autonomous team has no real VPS, VPS credential, provider console or public SSH endpoint during development. Real VPS validation starts only after the Principal creates `release/0.1.0` and the Owner runs `docs/owner-testing/OWNER_VPS_TEST_PROTOCOL.md`.

This constraint changes **evidence**, not product behavior:

- agents must still implement the complete approved workflows;
- agents must use deterministic stateful simulation, fault injection, golden fixtures, available local-contained OpenSSH integration and actual host packaging checks;
- no agent may claim real-VPS/UFW/systemd/reboot PASS before Owner evidence;
- expected absence of a VPS is not a blocker and cannot justify scope reduction or weak fake-success tests;
- every relevant result states evidence class E0–E5 from `docs/verification/BLIND_DEVELOPMENT.md`.

`release/0.1.0` means **READY FOR OWNER VPS TEST**, not already validated on a VPS.

## 3. Supported scope

### Local platforms

- Windows
- macOS
- Linux

Distributed artifacts are self-contained and do not require the end user to install .NET separately.

### Remote platform

- Ubuntu only for v0.1

Research/Principal will record the exact Ubuntu LTS versions whose command/output contracts are represented by fixtures and Owner testing. No non-Ubuntu distribution is part of v0.1 acceptance.

## 4. Core features

### F01 — Portable desktop application

Provide a native-style desktop application using C#/.NET and Avalonia UI.

Acceptance Criteria:

1. Self-contained Windows artifacts are produced for approved RIDs.
2. Self-contained macOS artifacts are produced for approved RIDs.
3. Self-contained Linux artifacts are produced for approved RIDs.
4. Artifacts do not require Node.js, Python, Docker, a browser runtime or separately installed .NET for normal use.
5. VPS-management logic is not implemented in UI views.
6. Startup failure produces a useful sanitized error and diagnostic path rather than silent exit when technically possible.
7. Every artifact contains version and source/build SHA metadata.
8. A target is described as built, package-inspected, startup-smoked or manually exercised only when that evidence actually exists.

### F02 — VPS connection and Test Connection

Connection form contains:

- Host or IP address
- SSH port, default 22
- Username
- Password authentication
- Alternative initial SSH private-key authentication (VP-123 extension below)
- Test Connection action

Acceptance Criteria:

1. User can enter host/IP, port, username and protected password.
2. Invalid host, port or missing values are rejected before SSH.
3. Production Test Connection attempts an actual SSH connection through the transport abstraction.
4. Success is shown only after authentication and minimum remote verification complete.
5. Authentication failure, timeout, refusal/unreachable, unknown host key, changed host key, cancellation and unexpected transport failure are distinguishable where practical.
6. Connection supports cancellation and finite timeout.
7. Password is not persisted or logged by default.
8. A successful session can be reused safely within the application session.
9. Changing connection identity invalidates stale session state.
10. Unknown host keys require explicit user trust; changed known keys fail closed until explicitly reviewed.
11. Blind development verifies this through E1/E2 and E3 local-contained protocol evidence where available; real VPS remains E5 Owner work.

#### F02 authentication extension — VP-123

Owner-approved design packet: documentation SHA
`8ddeae3e753849dc559b0dbcd6b697f422ba83cb`,
[KA-T01–12 contract](https://github.com/ZillionxBuilds/VPSReady/blob/8ddeae3e753849dc559b0dbcd6b697f422ba83cb/middleman/vps-readiness-key-auth/05_ACCEPTANCE_AND_DOD.md).
This new scope is implemented on a review branch; the old qualified `0df6b15`
Owner binary does not gain these features from a documentation update.

- Disconnected Connection selects exactly Password OR SSH private key. Initial
  key login needs no server password, `.pub` companion, key deployment or prior
  session. Both modes retain explicit host trust and authenticated minimum
  verification before main-session promotion; no password/keyboard-interactive/
  agent/alternate-key fallback is permitted.
- Required private-only formats: plain/encrypted OpenSSH Ed25519 and RSA
  2048/3072/4096; plain RSA PKCS#1 PEM. RSA uses SHA-2, not `ssh-rsa` SHA-1.
  Product subset rejects certificates, public files, PuTTY/agent formats and
  unsupported encryption/KDF parameters. Encrypted OpenSSH uses AES256-CTR /
  bcrypt with bounded rounds; local parsing never requests a server password.
- Select a regular, non-linked/reparse, readable file at most 256 KiB with
  restrictive permissions. Derive the canonical public-blob fingerprint from
  validated private bytes. Never create a missing companion or chmod the
  selected file. Existing deployment pair validation remains separate.
- Capture validated A in an owned in-memory session lease until disconnect.
  Replacing A's original path with B cannot change fresh-login/reconnect identity.
  Each authorized probe/reconnect builds a fresh active-method authentication
  graph, pins host trust, performs minimum verification and disposes its own
  connection; main session is not replaced. Missing lease is detected before
  reboot dispatch; no real machine is rebooted by blind tests.
- Form/owned buffers clear on completion/invalidation/disposal. Third-party
  SSH.NET objects and transient managed strings cannot all be guaranteed zeroed;
  they are not persisted, bound as plaintext or forwarded to diagnostics.
- Delayed identity/auth/key changes, cancellation, trust refusal, wrong unlock
  and rejected authentication cannot revive old session/trust/confirmation state.
  Stable initial-key errors contain no key bytes, passphrase, endpoint or path.

### F03 — Server overview

After a successful connection display, where available:

- distribution/version;
- kernel/architecture;
- hostname;
- uptime;
- remote user;
- root/sudo capability;
- CPU summary;
- total memory;
- root-disk summary;
- current SSH port;
- firewall availability/status.

Acceptance Criteria:

1. Production data comes from remote inspection, not local assumptions.
2. Unavailable fields show explicit Unknown/Unavailable rather than fabricated values.
3. Parsing handles approved Ubuntu fixture variation and predictable locale differences.
4. Inspection is read-only.
5. One failed field does not discard successful fields.
6. Remote output is treated as untrusted and bounded.
7. Refresh emits correlated diagnostics without leaking identifiers/secrets.

### F04 — Basic firewall management

Use UFW for Ubuntu v0.1.

Required actions:

- detect availability/status;
- enable;
- disable;
- list relevant allow rules;
- add TCP rule;
- add UDP rule;
- remove an explicitly selected rule.

Acceptance Criteria:

1. Absent, inactive, active and error states are distinct.
2. Relevant existing rules are listed with protocol, port/range, action, source and IPv4/IPv6 identity where available.
3. Valid TCP and UDP ports 1–65535 can be added.
4. Invalid values are rejected before command construction.
5. Add is idempotent and verified through refreshed state.
6. Removal requires explicit selected-rule action and confirmation.
7. Stale rule identity cannot silently delete another rule.
8. Enabling UFW first ensures the current SSH port is allowed and verifies the rule before enable.
9. Normal UI cannot remove/block the active SSH port without a separately defined verified migration flow.
10. Enable/disable/remove/add report success only after refreshed verification.
11. Cancellation/failure does not produce false success.
12. Blind tests exhaustively model UFW state and failure; only Owner E5 may claim real UFW/access preservation.

### F05 — Local SSH key generation

Required capabilities:

- generate ED25519 pair locally;
- choose/confirm file name/path;
- show/copy public key;
- prevent silent overwrite;
- use platform-appropriate restrictive permissions.

Acceptance Criteria:

1. Generated key format is interoperable with approved OpenSSH clients/servers.
2. Existing private key is never silently overwritten.
3. Pair writes are atomic enough to avoid misleading partial success.
4. Restrictive permissions are applied and verified where supported.
5. Public key may be viewed/copied intentionally.
6. Private key is never displayed by default.
7. Private key/passphrase never enters logs, diagnostics, screenshots or bundles.
8. Errors leave clear state and no orphaned partial pair where cleanup is safe.
9. Generation approach is maintained, license-compatible and documented; no homegrown cryptography.

### F06 — Install SSH public key on VPS

Allow password-connected user to install a selected/generated public key for the target account.

Acceptance Criteria:

1. Remote `.ssh` and `authorized_keys` are created when required.
2. Existing valid entries are preserved.
3. Correct ownership/secure permissions are applied.
4. Duplicate key deployment is idempotent.
5. Full key material is not logged or copied to diagnostics.
6. VPSReady opens a separate new connection using the private key.
7. Success is reported only after that separate key-authenticated connection verifies identity/minimum command.
8. Failed verification leaves password access unchanged and existing keys intact.
9. This feature never automatically disables password authentication.
10. Blind simulation models remote file/permission and verification failures; E3 may prove local protocol interoperability; Owner E5 proves real VPS behavior.

### F07 — Local SSH config management

Required fields:

- Alias / Host
- HostName
- User
- Port
- IdentityFile
- `IdentitiesOnly yes`

Acceptance Criteria:

1. Create config file when absent.
2. Add new alias without deleting unrelated entries/comments/line endings.
3. Existing alias collision is explicit; no silent overwrite.
4. Wildcards and OpenSSH first-obtained-value semantics are considered.
5. Selected private-key path is used safely.
6. Update uses backup/atomic replacement and does not truncate on failure.
7. Platform path and permission policy are applied.
8. Repeating the same desired alias is idempotent or yields an explicit no-change result.
9. Final safe summary is shown without dumping the entire user's SSH config into logs/bundles.

### F08 — Basic system actions

Provide:

- refresh package index;
- install available package upgrades;
- detect reboot-required;
- reboot and bounded reconnect;
- view/change hostname;
- view/change timezone.

Acceptance Criteria:

1. Read-only current state is shown before write where practical.
2. Package actions require explicit user action, expose progress and use finite timeout/cancellation semantics.
3. Apt lock/contention, privilege failure, nonzero exit and interactive blocker are distinguishable.
4. No distro release upgrade occurs.
5. No silent reboot occurs.
6. Reboot requires explicit confirmation; expected disconnect is not generic immediate failure.
7. Reconnect is bounded/cancellable and revalidates host identity.
8. Hostname and timezone input are validated and resulting state verified.
9. Cancellation does not falsely imply remote rollback.
10. Every action emits safe correlated diagnostics.

### F09 — Activity, operation journal and support diagnostics

Implement the binding contract in `docs/diagnostics/LOGGING_AND_SUPPORT_BUNDLE.md`.

Acceptance Criteria:

1. Activity page shows understandable started/running/succeeded/warning/failed/cancelled/recovery-required events.
2. Every remote workflow receives session/run/operation/step IDs.
3. Stable event, command and error IDs identify behavior without relying on raw messages.
4. Structured JSONL journals record applicable phase, action, status, duration, exit code, verification/recovery state and safe context.
5. Command output capture is policy-driven, redacted and bounded; truncation is explicit.
6. Password, passphrase, private key, token and credential-bearing raw command never reach UI, logs, exceptions, screenshots, test artifacts or bundles.
7. Host/IP/username are pseudonymized in public-safe reports by default.
8. Redaction occurs before every sink and fails closed by omitting unsafe payload.
9. Log storage uses per-user platform state paths, bounded retention and cleanup.
10. User can open log folder and clear diagnostics.
11. User can Copy Safe Issue Report containing release/build, stage, operation ID, error code and safe summary.
12. User can Export Sanitized Support Bundle with manifest, checksums, safe report, run summary, events and safe environment data.
13. Bundle excludes credentials, keys, full SSH config, known-host/trust contents, `authorized_keys`, raw server identity and unredacted output.
14. No diagnostic is auto-uploaded; no telemetry/backend is introduced.
15. Unexpected/startup failures provide a safe error ID, local diagnostic path and export option where possible.
16. Redaction adversarial tests prove seeded secrets do not appear in persisted/exported surfaces.
17. Owner can correlate a UI failure to exactly one operation journal using the operation ID.

### F10 — Safety and verification core

Acceptance Criteria:

1. Mutations follow `validate -> inspect/preflight -> plan -> explicit confirmation -> apply -> verify -> report/recovery` as applicable.
2. Security-critical configuration is backed up before modification when practical rollback exists.
3. SSH configuration is validated before reload/restart whenever modified by a supporting/future approved flow.
4. Firewall preserves active access according to `AGENTS.md`.
5. Resulting state is verified before success whenever practical.
6. Verification failure is explicit and invokes safe rollback/recovery when defined.
7. Remote operations use finite timeouts and cancellation where technically practical.
8. Repeating successful operation does not corrupt state or create uncontrolled duplicates.
9. Destructive/lockout-risk operations require explicit user intent.
10. No production path depends on a test fake or unconditional success.
11. Every failure produces an operation ID and actionable next step.
12. Simulation can inject failure at each phase and prove terminal state/diagnostics.

### F11 — Evidence-based VPS Ready checklist (VP-123)

Traceability: RC-T01–17 and UX-T01–06 in the pinned VP-123 acceptance contract.
Profile `core-basic-v1` v1.0 / Core Basic · Ubuntu / UFW. Explicit read-only
**Check VPS Ready / Cancel check**, never automatic monitoring or remediation.

Nine required observations: recognized Ubuntu; current trusted verified session;
separate new active-method login; actual permitted privileged reads; UFW active;
supported server-side SSH port/source/family policy plus new login; complete
zero-exit empty dpkg audit; writable root with >= 1 GiB available; complete
supported Ubuntu no-pending-reboot observation.

Six advisory observations: key-authenticated fresh login; cached upgrade count
with honest index provenance; actual valid hostname/timezone; actual NTP sync;
root available capacity (< 2 GiB or < 10% warns); actual 22.04/24.04 fixture
coverage, never inferred lifecycle/security-support expiry.

Provider firewall/rescue/snapshot/restore, workload DNS/TLS/ports/runtime and
server-wide password/MFA policy remain visibly MANUAL_NOT_ASSESSED/NOT_ASSESSED;
not score denominators or checkboxes that manufacture readiness.

Verdicts: NOT_CHECKED, CHECKING, STALE, UNSUPPORTED_PROFILE, INCOMPLETE,
NEEDS_ATTENTION, READY_WITH_WARNINGS, READY. Missing/duplicate/contradictory
policy or required unknown/error/not-run/not-applicable never becomes Ready.
Positive required FAIL on a completed inspection means NeedsAttention; cancelled,
overall-timeout, failed-collector or required-journal failure means Incomplete.
All nine required PASS are necessary. Cached zero-upgrades does not prove current
upstream security; unknown freshness warns. No apt update/check/cache write.

Freshness is at most 300 monotonic seconds, not restored by wall-clock rollback.
Disconnect/reconnect/identity/auth/key/profile change, new Check, any operation
that may mutate (including failed/cancelled dispatch) and suspend/resume invalidate
the report. No stale async completion can restore it. Ordinary tab navigation
does not mutate/recheck. Default read budget 10s, entire fresh login including
disposal 20s, entire Check 120s; cap all probes by remaining deadline and serialize
with session operations. One attempt per explicit Check, one authoritative
terminal event; redacted correlation and scoped Safe Issue Report/support bundle.

Typed per-row destinations are existing page + section + check ID + session +
generation only. Navigation focuses/scrolls safe guidance and never changes
endpoint/port/key/source/config fields, checks confirmations, refreshes data or
dispatches a fix. Stale context is discarded; after an explicit separate change,
Back to VPS Ready requires explicit recheck. Read-only storage/privilege/time
guidance adds no out-of-scope repair operations. Source-restricted/range/custom
firewall ambiguity is UNKNOWN, not a reason to expand a source to Anywhere.

DoD A: all 35 KA/RC/UX acceptance IDs plus E0/full E1/full E2/actual contained
key-only E3/exact-SHA self-contained Mac review-package/native offline E4, existing
R1–R19 safety/privacy, current Workpad/spec/guide/manual addendum and explicitly
SELF_REVIEW (not independent QA). Terminal is
KEY_AUTH_READINESS_READY_FOR_EXTERNAL_REVIEW, not Owner-package acceptance or
main readiness. External review and authorized integration/new candidate are
separate Phase B. No automatic release/main merge or stable publication.
REAL VPS: NOT TESTED.

## 6. UX requirements

1. Primary workflows are understandable without Linux-command knowledge.
2. Risky actions explain intended change before execution.
3. Destructive/lockout-risk actions require explicit intent.
4. Long actions show responsive progress and cancellation where honest.
5. Validation appears near relevant fields/actions.
6. Primary results are user language; safe technical details remain available through diagnostics.
7. No success before verification.
8. Failures show stable error/operation ID and safe next action.
9. Test-only scenario mode is unmistakably marked and is never present as a hidden production success path.
10. Public issue-report flow warns that the GitHub repository is public.

## 7. Security and privacy requirements

1. Password credentials are session-only by default.
2. Passwords/private keys/tokens are absent from persisted state, logs, crash data and repository fixtures.
3. Only public keys are deployed remotely.
4. Existing `authorized_keys` entries are preserved.
5. Host identity handling is explicit and fail-closed on change.
6. No operation knowingly leaves user locked out when prevention/verification is possible.
7. Remote output is untrusted and cannot inject unsafe UI/log formatting or shell arguments.
8. Diagnostics are local-only unless user explicitly exports/shares them.
9. Public-safe reports pseudonymize server/user identity.
10. The app offers no unredacted export mode in v0.1.

## 8. Architecture constraints

1. C#/.NET and Avalonia remain the stack.
2. Remote SSH/Linux behavior is behind testable interfaces.
3. Views do not contain broad raw shell/SSH logic.
4. Stable command/event/error catalogs exist.
5. Stateful scenario host implements the same application-facing contracts and fails on unknown commands.
6. Production binaries do not ship test credentials or fake success controls.
7. Diagnostics/redaction are centralized, independently tested services.
8. Remote VPS requires no permanent agent.
9. Prefer small understandable project boundaries over speculative layering.

## 10. Exit criteria to create `release/0.1.0`

Principal may create the release branch only when:

1. F01–F10 are implemented.
2. All applicable feature AC and global blind DoD pass.
3. Gate A and Gate B are `BLIND_PHASE_APPROVED`.
4. Gate C full E0–E4 regression and final simulated Manual QA pass.
5. No unresolved P0/P1, security, privacy, false-success, data-loss, lockout-policy or release blocker remains.
6. Candidate artifacts/checksums are tied to exact development SHA.
7. Diagnostics/support-bundle/Safe Issue Report DoD passes.
8. User/troubleshooting and Owner VPS test instructions match implementation.
9. Known real-infrastructure uncertainties are explicit.
10. No v0.1 non-goal became a required dependency.

Principal records:

- `READY_FOR_OWNER_VPS_TEST`;
- `REAL VPS: NOT TESTED`;
- exact branch/SHA/artifacts/checksums;
- Owner test and recovery prerequisites.

## 11. Exit criteria for stable `main`

Stable promotion is separate from release-branch creation and requires:

1. Owner tests exact candidate according to staged protocol.
2. Release-blocking E5 stages PASS or Owner explicitly accepts a named limitation.
3. Owner failures are fixed, blind-regressed, Principal re-approved and Owner-retested.
4. No unresolved P0/P1/lockout/secret-leak/data-loss defect.
5. Owner explicitly authorizes promotion.

Silence or internal PASS is not Owner approval.

## 12. Autonomous execution guidance

Within scope, agents make ordinary implementation decisions independently and continue until blind release readiness.

Priority order:

1. safety;
2. correctness;
3. diagnostic ability;
4. testability;
5. maintainability;
6. cross-platform reliability;
7. simplicity;
8. performance optimization.

Do not stop for cosmetic/low-risk internal choices. Do not request a VPS. Do not weaken scope or evidence language. Owner will first interact with the product at `release/*` real-VPS validation.
