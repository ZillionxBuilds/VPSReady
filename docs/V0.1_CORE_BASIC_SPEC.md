# VPSReady v0.1 Core Basic Specification

Status: Approved development scope for `development`

This document is the implementation contract for VPSReady Core Basic v0.1. Autonomous development must remain within this scope unless the owner explicitly changes it.

## 1. Product Goal

VPSReady v0.1 is a portable cross-platform desktop application that helps a user connect to a fresh Ubuntu VPS, inspect it, establish safe SSH access, manage basic firewall rules, perform basic system actions, and leave the VPS in a usable and safer state without requiring the user to memorize Linux commands.

The application runs locally on Windows, macOS, and Linux and manages the VPS over SSH. No permanent VPSReady agent or daemon is installed on the remote server.

## 2. Supported Scope

### Local platforms

- Windows
- macOS
- Linux

The distributed desktop application must be self-contained and must not require the end user to install the .NET runtime separately.

### Remote platform

- Ubuntu only for v0.1

The implementation may be structured for future distro support, but no other distro is part of v0.1 acceptance.

## 3. Core Features

### F01 — Portable Desktop Application

Provide a native-style desktop application using C#/.NET and Avalonia UI.

Acceptance Criteria:

1. A self-contained Windows build can launch without a separately installed .NET runtime.
2. A self-contained macOS build can launch without a separately installed .NET runtime.
3. A self-contained Linux build can launch without a separately installed .NET runtime.
4. The application has no dependency on Node.js, Python, Docker, or a browser runtime for normal end-user execution.
5. VPS-management logic is not implemented directly inside UI views.
6. Application failure during startup produces a useful sanitized error rather than silently exiting.

### F02 — VPS Connection and Test Connection

Provide a connection form containing at minimum:

- Host or IP address
- SSH port, default 22
- Username
- Password authentication
- Test Connection action

Acceptance Criteria:

1. The user can enter host/IP, port, username, and password.
2. Invalid host, port, or empty required values are rejected before attempting SSH.
3. Test Connection attempts a real SSH connection.
4. Success is shown clearly to the user.
5. Authentication failure, timeout, unreachable host, host-key problem, and other common SSH failures produce distinguishable user-facing errors where practical.
6. Connection attempts support cancellation and a finite timeout.
7. Password values are not written to logs or persisted by default.
8. A successful Test Connection can be reused by subsequent server-inspection actions without forcing unnecessary credential re-entry during the same application session.

### F03 — Server Overview

After a successful connection, display useful server information.

Required information where available:

- Distribution and version
- Kernel / architecture
- Hostname
- Uptime
- Current remote user
- Root or sudo capability
- CPU summary
- Total memory
- Disk/root filesystem summary
- Current SSH port
- Firewall status

Acceptance Criteria:

1. Information comes from the connected VPS rather than local-machine assumptions.
2. Unsupported or unavailable fields show an explicit unavailable/unknown state rather than fabricated values.
3. Parsing is resilient to expected Ubuntu output variations.
4. Inspection is read-only and does not change the VPS.
5. Failure to retrieve one information field does not unnecessarily invalidate all successfully retrieved fields.

### F04 — Firewall Basic Management

Provide a firewall panel for Ubuntu using the supported firewall mechanism selected by the implementation.

Required actions:

- Detect firewall availability/status
- Enable firewall
- Disable firewall
- List allowed rules/ports in a user-understandable form
- Add an allow rule for a port
- Remove a rule created/selected by the user
- Support TCP
- Support UDP

Acceptance Criteria:

1. The user can view whether the firewall is active or inactive.
2. Existing relevant allow rules can be listed.
3. The user can add a valid TCP port rule.
4. The user can add a valid UDP port rule.
5. Invalid ports outside 1-65535 are rejected.
6. Removing a rule requires an explicit user action.
7. Enabling the firewall first ensures that the current SSH port is allowed.
8. The active SSH port cannot be removed/blocked through a normal rule-removal flow without a safe replacement-connectivity workflow.
9. Firewall state is verified after enable/disable/rule changes before reporting success.
10. Repeating an already-satisfied allow operation does not create uncontrolled duplicate configuration.

### F05 — Local SSH Key Generation

Provide a local SSH key-management function.

Required capabilities:

- Generate an ED25519 key pair locally
- Allow the user to choose or confirm a file name/path
- Show/copy the public key
- Detect path collisions and avoid silently overwriting an existing key

Acceptance Criteria:

1. A valid ED25519 key pair can be generated on each supported local platform.
2. Existing private-key files are never silently overwritten.
3. File permissions are set appropriately where the platform supports Unix-style permissions.
4. The public key can be viewed or copied.
5. The private key is not displayed by default.
6. Private key content is never written to logs.
7. Errors leave no misleading success state.

### F06 — Install SSH Public Key on VPS

Allow a user connected with password authentication to install a selected/generated public key on the remote account.

Acceptance Criteria:

1. The remote `~/.ssh` directory is created if required.
2. `authorized_keys` is created if required.
3. Correct ownership and secure permissions are applied for the target account.
4. Installing an already-present public key does not add duplicate entries.
5. After installation, VPSReady opens a separate new SSH connection using the private key.
6. The feature reports success only after key-based authentication has been verified with that new connection.
7. Failure to verify key login keeps password access unchanged.
8. No automatic disabling of password authentication occurs as part of this feature.

### F07 — Local SSH Config Management

Provide a UI for adding a host alias to the local OpenSSH config.

Required fields:

- Alias / Host
- HostName
- User
- Port
- IdentityFile

Expected generated settings include `IdentitiesOnly yes` unless there is a documented compatibility reason not to use it.

Acceptance Criteria:

1. VPSReady can create the local SSH config file when absent.
2. It can add a new alias without deleting unrelated existing entries.
3. Duplicate alias handling is explicit; an existing alias is not silently overwritten.
4. Resulting configuration uses the selected private-key path.
5. File updates are performed safely and do not truncate unrelated SSH config content.
6. The user can see the final alias/configuration summary after creation.

### F08 — Basic System Actions

Provide a minimal System panel with the following actions:

- Refresh package index
- Install available system package upgrades
- Detect whether a reboot is required
- Reboot server
- View/change hostname
- View/change timezone

Acceptance Criteria:

1. Read-only state is shown before corresponding write actions where practical.
2. Package operations expose progress/status and do not claim completion before the remote command completes.
3. Package-manager lock/contention is reported clearly.
4. Reboot requires an explicit user action.
5. After reboot is requested, the previous SSH disconnection is treated as expected rather than reported as an immediate generic failure.
6. VPSReady can attempt to reconnect and verify availability after reboot without an infinite wait.
7. Hostname changes are verified after application.
8. Timezone values are validated against available server timezones before being applied.

### F09 — Activity and Diagnostic Log

Provide an activity view/log for operations performed during the application session.

Acceptance Criteria:

1. Connection, inspection, firewall, SSH-key, SSH-config, and system actions produce meaningful status entries.
2. Entries distinguish started, success, warning, and failure states.
3. Passwords are never logged.
4. Private SSH key material is never logged.
5. Secrets embedded in exception messages or command arguments are redacted before display/persistence.
6. Logs contain enough sanitized context to troubleshoot common failures.

### F10 — Safety and Verification Core

Safety behavior is part of the product, not an optional enhancement.

Acceptance Criteria:

1. Security-critical configuration is backed up before modification when a practical rollback path exists.
2. SSH configuration is validated before reload/restart whenever VPSReady modifies it in a future or supporting flow.
3. Firewall operations preserve current SSH access as defined in `AGENTS.md`.
4. Operations verify resulting state before reporting success whenever practical.
5. Failed verification yields a clear failure state and attempts rollback where the operation has a safe defined rollback path.
6. Remote operations use finite timeouts and support cancellation where technically practical.
7. Re-running an already successful operation does not corrupt configuration or create uncontrolled duplicates.
8. No UI path reports success based only on command dispatch when resulting state can reasonably be checked.

## 4. Explicit Non-Goals for v0.1

The following are NOT part of Core Basic v0.1 and must not be added by autonomous scope expansion:

- Docker Engine or Docker Compose installation
- Coolify
- Kubernetes
- Nginx/Apache web-server provisioning
- PostgreSQL/MySQL/Redis or other database provisioning
- Fail2ban installation or advanced configuration
- Automatic security-update configuration wizard
- Swap creation/tuning
- Cloud-provider APIs
- Provider snapshot automation
- DNS management
- TLS/SSL certificate automation
- Monitoring/observability platforms
- Application deployment workflows
- Hosted VPSReady backend/service
- VPSReady remote daemon/agent
- User accounts, cloud sync, telemetry, analytics, or advertising
- Support for non-Ubuntu remote distributions

A non-goal may become a later module or milestone only after explicit owner approval.

## 5. UX Requirements

1. The primary workflow must be understandable without requiring the user to know Linux commands.
2. Risky actions must communicate what will change before execution.
3. Destructive or lockout-risk actions require explicit user intent.
4. Long-running actions must provide visible progress or status.
5. The UI must remain responsive during remote operations.
6. Validation errors should appear close to the relevant input/action.
7. Raw shell output may be available for diagnostics, but the primary result must be expressed in user-understandable terms.
8. The application must not present a server as successfully changed until verification has completed when verification is available.

## 6. Security Requirements

1. Password authentication credentials live in memory only by default.
2. Passwords must not be written to local settings, logs, crash reports, or repository files.
3. Private SSH keys remain local and are never uploaded except when technically required by a future explicitly approved feature; Core Basic uploads public keys only.
4. Public-key installation must preserve valid existing `authorized_keys` entries.
5. No operation may knowingly leave the user locked out when VPSReady can detect or prevent the condition.
6. No personal credentials or live VPS secrets may exist in automated test fixtures committed to Git.
7. Host-key verification behavior must be explicit and must not silently train users to ignore host identity changes.

## 7. Architecture Constraints

1. C#/.NET remains the implementation language/runtime.
2. Avalonia UI remains the desktop UI technology.
3. Remote SSH and Linux operations must be behind testable abstractions/services.
4. UI views must not directly contain a broad collection of raw SSH/shell commands.
5. The design must allow a future CLI or additional modules to reuse core/application logic without rewriting the product.
6. The remote VPS must not require a permanently installed VPSReady process.
7. Prefer a small, understandable project structure over speculative enterprise-style layering.

## 8. Global Definition of Done

A feature is Done only when all applicable items below are true.

### Implementation

- The feature is fully implemented for its approved v0.1 scope.
- There is no fake-success path or required placeholder implementation.
- User-facing errors are handled for expected failure modes.
- Cancellation/timeouts are implemented where the operation can block on network/remote execution.

### Acceptance

- Every feature-specific Acceptance Criterion passes.
- Applicable security and safety requirements pass.
- Applicable UX requirements pass.

### Quality

- `dotnet build` succeeds for the solution in the supported development environment.
- Automated tests pass.
- New behavior has meaningful automated coverage at the appropriate layer.
- Critical logic is not validated only by implementation code with no independent test.
- Static analysis/compiler warnings introduced by the feature are resolved unless explicitly justified.

### Security

- No passwords, private keys, tokens, or live credentials exist in committed code/tests/docs.
- Logs and exceptions are checked for secret leakage.
- Firewall/SSH changes satisfy lockout-prevention invariants.

### Maintainability

- Code is reasonably separated between UI, application/core behavior, and infrastructure/SSH concerns.
- Public/internal behavior that future contributors need to understand is documented where appropriate.
- Repeated remote operations are idempotent where practical.

### Validation

- Unit tests cover validation/parsing/application logic as applicable.
- Integration tests cover SSH/remote-command behavior where practical.
- UI/view-model workflows have automated coverage where practical.
- Before v0.1 is promoted to a release branch, real Ubuntu VPS/VM E2E validation must cover at minimum connection, public-key installation/key-login verification, and firewall safety behavior.

A passing build alone is not Definition of Done.

## 9. v0.1 Release Exit Criteria

`development` may be considered ready to cut `release/0.1.0` only when:

1. F01-F10 are implemented.
2. All acceptance criteria applicable to v0.1 pass.
3. Global Definition of Done is satisfied.
4. No known blocker or critical defect remains open.
5. No known SSH/firewall lockout defect remains open at any severity.
6. Supported local-platform build artifacts are produced successfully.
7. Real Ubuntu validation has demonstrated the critical connection, SSH-key, and firewall flows.
8. Documentation accurately reflects the implemented product.
9. No v0.1 non-goal was silently introduced as a required dependency.

Promotion from `release/0.1.0` to `main` remains an owner decision.

## 10. Autonomous Execution Guidance

Within this specification, Codex/autonomous agents are expected to make ordinary implementation decisions independently and continue working until the scope and tests are complete.

When multiple reasonable internal approaches exist, prefer in this order:

1. Safety
2. Correctness
3. Testability
4. Maintainability
5. Cross-platform reliability
6. Simplicity
7. Performance optimization

Do not stop for cosmetic or low-risk internal choices that can be resolved using these priorities. Do stop scope expansion at the boundaries defined by this specification and `AGENTS.md`.
