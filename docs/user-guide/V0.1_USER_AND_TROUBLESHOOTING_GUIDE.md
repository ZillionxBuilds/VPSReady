# VPSReady v0.1 User and Troubleshooting Guide

[Project home](../../README.md) · [Documentation](../README.md) · [Project status](../PROJECT_STATUS.md)

Status: pre-release user guide. Check the current candidate and evidence before testing.

VPSReady is a local desktop application for managing an **Ubuntu** server over
SSH. It has no hosted control plane, remote agent, telemetry, or automatic
diagnostic upload. It is not a provider-console replacement and does not
support non-Ubuntu distributions in v0.1.

> **Evidence boundary:** development evidence is local, simulated, contained
> protocol, and packaging evidence only. **REAL VPS: NOT TESTED.** Do not treat
> this guide, a green build, or a simulated result as proof that a real server
> is safe to change. Real-infrastructure testing requires an exact candidate
> and current Owner-test readiness in the release tracker; then follow the
> [Owner Real-VPS Test Protocol](../owner-testing/OWNER_VPS_TEST_PROTOCOL.md).

## Before you start

- Use an Ubuntu server that you are authorized to administer. Until the exact
  candidate is approved for Owner testing, do not use it against a real VPS.
- Keep an independent recovery route for a future Owner test: provider console
  or rescue path, a snapshot when available, and a separate ordinary SSH
  session for firewall and key changes. Do not put any of those details in a
  GitHub issue or a support bundle.
- Use only an artifact whose manifest, SHA-256 checksum, version, and source
  SHA match the release-candidate instructions. A candidate archive may be
  unsigned; inspect its `PACKAGE_NOTICE.md` and platform security prompts.
- Candidate packaging and startup evidence are separate. A package can be
  built and inspected without having been startup-smoked on that host. Consult
  the [dated evidence snapshot](../PROJECT_STATUS.md) and current Workpad for
  the exact artifact's startup result. Older C606/package evidence does not
  establish readiness for a newer artifact.

VPSReady starts disconnected. It does not save the connection password by
default, and the shell clears password input after a connection attempt.

## Connection, host trust, and overview

1. Open **Connection** and enter the host or IP, SSH port, username, and
   password. Connection input is checked before it is used.
2. Choose **Test Connection**. A success means authentication and the minimum
   remote verification completed; it is not shown before that verification.
3. A first-seen or changed host key fails closed and opens an explicit review
   panel with the observed host, port, algorithm, and fingerprint. For a
   first-seen key, review those values and choose **Trust host key** only when
   they are expected. For a changed key, do not choose **Replace trusted host
   key** unless you have independently verified the change. Never bypass this
   review by editing trust data out of band.
4. Saving a reviewed trust decision does not create a session. Re-enter the
   password and choose **Test Connection** again; success is shown only after
   authentication and verification.
5. The current **Overview** surface reports the safe connection/overview state,
   including `Unknown` when remote facts have not been refreshed. It does not
   yet render the full server-fact list in the desktop UI. Do not infer remote
   facts from local information; disconnect when finished.

Connection can report invalid input, authentication failure, refusal or
unreachability, timeout, cancellation, trust failure, or a safe unexpected
failure. Record the displayed operation ID before retrying. Do not paste a
password, raw server address, user name, fingerprint, or terminal transcript
into public support material.

The protected password surface consumes committed framework text, not a US-key
mapping. Caps Lock, Shift, and keyboard-layout text are not rewritten. Backspace
removes the last Unicode scalar, Escape clears the buffer, and Tab/Shift+Tab
retain normal focus navigation. Clipboard paste is explicitly unsupported on
this surface; the application never reads the clipboard for a password. Control
characters, invalid Unicode, or input over 4096 UTF-16 code units are refused and
the buffer is cleared. Framework text events are transient managed strings; the
app does not bind or retain their plaintext. Native IME/composition behavior on
each desktop OS still needs Owner UX testing; automated final-text tests are
not a claim of native keyboard/IME certification.

## Firewall

The **Firewall** page is available only with a verified session. Refresh the
state and current rules first; a disconnected or stale session is not a basis
for a change.

- Select TCP or UDP, IPv4 or IPv6, enter a valid port and permitted source, and
  choose **Add verified allow rule**. The application reports success only
  after refreshed verification.
- For removal, select the current rule, check the explicit confirmation, and
  choose **Remove selected rule**. Do not remove a rule just because a similar
  rule appears in an old screenshot or report.
- Enabling or disabling the firewall requires a separate confirmation. Before
  enabling it during Owner testing, make sure the active SSH port has been
  planned, allowed, and verified, and keep the independent control session
  open.
- The normal flow blocks removal of a TCP rule for the active SSH port. Treat a
  refusal as a safety result, not a prompt to alter rules out of band.

Cancel a running operation rather than starting a second one. A cancellation,
failure, or verification failure is not a successful change and does not imply
that a remote mutation rolled back. Refresh the state, preserve access, and
use the diagnostics path below before deciding on recovery.

UFW reads require root or available passwordless sudo, just like mutations.
Missing UFW, denied privilege, and malformed output are different failures.
The protected SSH port comes from the server side of the authenticated session,
not the port entered on the client (which may be translated by NAT). If that
evidence is unavailable, the normal enable/removal flows fail closed.

Before enable, the app inspects stored IPv4/IPv6 rules independently. A single
`ufw show added` line does not prove both families exist. IPv6 configuration is
read, never enabled implicitly. This path supports stock UFW 0.36.1/0.36.2
framework files with ordinary allow rules; custom hooks, conflicting rules and
unknown layouts require administrator review. Do not remove custom protection
just to bypass a refusal. Stored UFW checks do not validate provider firewalls,
other firewall managers or end-to-end reachability. Avoid concurrent external
firewall changes and keep the independent control session open.

## SSH keys and local OpenSSH aliases

Open **SSH Keys & Config** to generate a local Ed25519 key or select an
existing local key. VPSReady shows safe key metadata such as its algorithm and
fingerprint; it does not display private-key material in this surface or in
Activity.

For deployment, connect to and verify the intended server first, select the
key, check the explicit deployment confirmation, and choose **Deploy and
verify public key**. Deployment completes only after VPSReady refreshes and
verifies the public key's presence, ownership, and secure permissions on the
current verified session. It then remains a separately actionable
**PublicKeyDeployed** state; deployment alone does not prove that a new
key-authenticated connection works.

Choose **Test separate key authentication** next to test that selected key on a
new connection to the same trusted host. Only this separate action reports
key-authentication success. Neither action disables password authentication.
If the separate test fails, retain the existing password access and use that
safe access path to investigate.

For a local alias, enter the alias, host name, user name, and port, explicitly
confirm the save, then choose **Save verified local alias**. Existing aliases
and unrelated local SSH configuration are protected from silent overwrite.
Do not copy an entire SSH config, private key, full public key, or local path
into a public issue or support material.

Alias insertion keeps global settings before the first `Host` block. Configs
with `Include`, `Match`, continuation lines, or conflicting global managed
settings are refused unchanged for explicit review. Backups preserve the
original text, including line endings and UTF-8 BOM when present.

Public-key installation preserves existing records and appends a missing line
separator before a new record. Comments do not count as deployed keys. An
existing selected key with options/restrictions is refused for review instead
of adding an unrestricted duplicate. The installer refuses symlinks, foreign
ownership, and unsupported permissions rather than taking over the files.
For existing files it retains a same-directory
`.vpsready-authorized-keys.backup.*` recovery copy, stages a complete replacement,
checks for stale contents, and atomically renames it. A cooperative lock prevents
overlapping VPSReady installations; it cannot exclude an unrelated external
writer racing the final rename. Do not edit the file concurrently. After a
failure, recovery rechecks state; it does not automatically overwrite the
current file with a backup or claim rollback. Review recovery copies only via
your existing safe access path; never attach their contents to an issue.

## System actions

The **System** page is available with a verified server session. It provides
package-index refresh, package-upgrade planning and application,
reboot-required inspection, explicit reboot with bounded reconnect, and
hostname and timezone planning/change flows. Each mutation follows the same
safe sequence: read the current state, review the plan where applicable,
explicitly confirm the change, apply it, and wait for verification before
treating it as successful.

- For packages, choose **Read upgrade plan**, review the normal package plan,
  check the confirmation, then choose **Apply and verify package upgrade**.
  Package actions never offer a distribution release upgrade.
- For reboot, inspect whether a reboot is required, check the explicit reboot
  confirmation, then choose **Reboot and verify reconnect**. VPSReady never
  reboots silently; expected connection loss is followed by bounded reconnect
  and host-identity revalidation.
- For hostname or timezone, validate and read the plan first, explicitly
  confirm the reviewed change, then apply and verify it.

Use **Cancel operation** only for a running action. Cancellation, failure, or
recovery-required status does not claim that a remote change rolled back;
refresh the relevant state, preserve safe access, and follow the displayed
next safe action before retrying. Use the operation ID in **Activity &
Diagnostics** to prepare a Safe Issue Report or an explicitly local sanitized
support bundle. No raw command, endpoint, credential, or secret is displayed
or uploaded.

Package-index updates request strict repository-error handling; stale cache
files alone cannot prove a fresh update. An upgrade succeeds only after a
successful empty `dpkg --audit` and a valid reboot-required check. Generic apt
exit 100 is not labelled a lock unless bounded error evidence identifies lock
contention. Command deadlines are 10 minutes for index update, 2 minutes for
planning, and 60 minutes for upgrade application (with a 65-minute enclosing
session-operation deadline). Timeout/cancellation can leave package state
uncertain: do not assume rollback or blindly repeat the mutation.

Upgrade runs with an explicit minimal environment at the root/sudo boundary
(`DEBIAN_FRONTEND=noninteractive`, C locale and a fixed system PATH), without
inheriting arbitrary apt configuration environment variables or changing
sudoers. Modified dpkg conffiles are kept with `--force-confold`; new vendor
versions may remain as `.dpkg-dist` for later administrator comparison. The
reviewed plan displays this policy. This does not promise that every package
maintainer script preserves all configuration: unsupported interactions receive
EOF, and a nonzero exit, timeout or cancellation remains a failure/uncertain
partial state. No automatic retry, remote-process termination or rollback is
claimed. Inspect safe diagnostics and current state before any further action.

## Activity, safe reports, and support bundles

Open **Activity & Diagnostics** for the local activity list. Entries contain
safe state, action, message, and operation ID; use the filter to find an
operation. Selecting an entry also shows its run ID and duration before report
or bundle export is scoped to that safe correlated run. The current Activity
surface does not render an error code or an operation-specific next safe
action; its selected-detail fallback can say that no additional action is
required. Use the originating operation surface and verified refresh for the
specific recovery decision. VPSReady never uploads diagnostics automatically.

| Action | What it does | Important limit |
| --- | --- | --- |
| **Refresh activity** | Refreshes the bounded local safe activity list. | It is not remote monitoring. |
| **Open log folder** | Opens the local diagnostics folder, or shows its local path if opening fails. | Review files before sharing. |
| **Clear diagnostics** | Removes local journals and run data. | It does not delete previously exported bundles. |
| **Copy Safe Issue Report** | Copies a sanitized Markdown report intended for a public GitHub issue. | Review every attachment; the repository is public. |
| **Export Sanitized Support Bundle** | Prompts for a local folder and creates a new local ZIP. | It is never uploaded or attached automatically. |

The journal records safe correlation and workflow information such as
session/run/operation/step IDs, stable event/command/error IDs, phase, result,
duration, and allowed bounded output. Redaction runs before the Activity view,
local journal, report, or bundle. If safe redaction cannot be guaranteed, the
payload is omitted instead of exported.

The bundle contains a manifest with SHA-256 checksums, a safe issue report,
run summary, redacted events, safe environment information, and known
limitations. It excludes passwords, passphrases, tokens, private keys, full
public keys, local SSH configuration, trust data, `authorized_keys`, raw
server identity, provider details, unrelated files, and unredacted output.
Retention applies to local journal data; exported bundles remain local and are
not automatically deleted.

## Safe troubleshooting path

1. Stop before repeating a risky operation. For firewall and SSH access work,
   first confirm that your independent recovery path and existing access still
   work.
2. In **Activity & Diagnostics**, select the related entry and capture its
   operation ID, state, run ID, and duration. If the originating **Firewall**
   or **SSH Keys & Config** surface displays an error code, capture it there;
   Activity itself does not display that code.
3. Follow the originating operation surface's status and eligibility message,
   then refresh the relevant verified state. A failed/cancelled/partial
   operation must not be assumed to have changed nothing or to have rolled
   back.
4. Use **Copy Safe Issue Report**. If more diagnosis is necessary, use
   **Export Sanitized Support Bundle** to an explicit local folder, inspect it,
   and share it only deliberately.
5. In a public issue, describe the action, expected result, observed safe
   summary, operation ID, exact candidate SHA, local platform, and whether
   access remains available. Include an error code only when it is shown on
   the originating surface or in reviewed safe report/bundle material. Never
   include credentials, key material, raw server identity, SSH config,
   provider details, or raw logs.

For a startup problem, VPSReady should enter a safe limited state with an
opaque startup error ID rather than exposing an exception. Restart the app; if
the condition persists, use the local diagnostics path when available and
share only a reviewed Safe Issue Report. Do not attempt to extract or publish
raw crash data.

## Owner real-VPS test boundary

Only the Owner tests a real VPS, and only after the Principal has created the
exact `release/0.1.0` candidate and the release tracker says
`READY_FOR_OWNER_VPS_TEST`. Use the staged
[Owner Real-VPS Test Protocol](../owner-testing/OWNER_VPS_TEST_PROTOCOL.md):
verify artifact provenance first, validate diagnostics before risky actions,
then test connection, firewall, SSH access, system actions, repeat/recovery,
and a final reviewed bundle on a fresh disposable Ubuntu VPS.

If recovery access is unavailable, mark the affected test
`BLOCKED_ENVIRONMENT`; do not force a lockout-risk action. Owner outcomes are
`PASS`, `FAIL`, `BLOCKED_ENVIRONMENT`, or `NOT_RUN`; simulated, local-contained
SSH, CI, and packaging results are never an Owner real-VPS pass.

**REAL VPS: NOT TESTED.**
